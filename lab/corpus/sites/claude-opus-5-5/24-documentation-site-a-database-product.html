Introduction to Basalt

Basalt is a distributed, PostgreSQL-compatible SQL database built for real-time workloads. It gives you strong consistency, automatic sharding, and sub-millisecond reads — without giving up the SQL you already know.

Why Basalt?

  • Serializable by default. Every transaction runs at the strictest isolation level, across shards and regions.
  • Horizontal scale. Tables split into ranges that rebalance automatically as you add nodes.
  • Wire-compatible with PostgreSQL. Use psql, your existing ORM, and most Postgres drivers unchanged.
  • Hybrid storage. Row-oriented storage for OLTP, with optional columnar projections for analytics.
  • Survives failure. Raft-based replication tolerates node, zone, or region outages with zero data loss.

Architecture at a glance

A Basalt cluster is a set of identical nodes. Each node runs the SQL layer, the distributed transaction coordinator, and a local storage engine. There is no primary node and no external coordinator to manage.

LayerResponsibility
SQL gatewayParses, plans, and optimizes queries; speaks the Postgres wire protocol.
Transaction layerCoordinates multi-range transactions using hybrid logical clocks.
Distribution layerMaps keys to ranges and routes requests to range leaseholders.
Replication layerReplicates each range across nodes with Raft consensus.
Storage engineLSM-tree key-value store on local disk.

What's new in 4.2

  • Columnar projections are now generally available.
  • Incremental backups to any S3-compatible bucket.
  • basalt doctor diagnoses common cluster misconfigurations.
  • Up to 38% lower p99 write latency on multi-region tables.

Upgrading

Basalt supports rolling upgrades between adjacent minor versions. Upgrade one node at a time and wait for basalt node status to report all ranges healthy before moving on.

WarningSkipping minor versions (for example 4.0 → 4.2) is not supported. Upgrade to 4.1 first.

Quickstart

Start a local Basalt node, create a table, and query it — all in about five minutes.

Start a node

  1. Start a single-node cluster in insecure mode (for local development only):

    basalt start --single-node --insecure --store=./basalt-data

  2. In a new terminal, open the built-in SQL shell:

    basalt sql --insecure

  3. Open the admin console at http://localhost:8080 to watch metrics in real time.

Create your first table

CREATE DATABASE shop;
USE shop;

CREATE TABLE products (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name       TEXT NOT NULL,
  price      DECIMAL(10, 2) NOT NULL,
  tags       TEXT[],
  created_at TIMESTAMPTZ DEFAULT now()
);

INSERT INTO products (name, price, tags) VALUES
  ('Mechanical keyboard', 129.00, ARRAY['hardware', 'input']),
  ('USB-C hub',            49.50, ARRAY['hardware']),
  ('Desk lamp',            34.99, ARRAY['office']);

Query your data

SELECT name, price
FROM products
WHERE 'hardware' = ANY(tags)
ORDER BY price DESC;
        name         | price
---------------------+--------
  Mechanical keyboard | 129.00
  USB-C hub           |  49.50
(2 rows)

Connect from your app

import basalt

conn = basalt.connect("basalt://root@localhost:5433/shop?sslmode=disable")
with conn.cursor() as cur:
    cur.execute("SELECT name, price FROM products")
    for name, price in cur:
        print(name, price)
import { Client } from "@basalt/client";

const db = new Client("basalt://root@localhost:5433/shop?sslmode=disable");
const { rows } = await db.query("SELECT name, price FROM products");
console.table(rows);
db, err := basalt.Open("basalt://root@localhost:5433/shop?sslmode=disable")
if err != nil {
    log.Fatal(err)
}
rows, _ := db.Query(ctx, "SELECT name, price FROM products")
defer rows.Close()

Data Model

Basalt presents a relational interface on top of a sorted, distributed key-value store. Understanding this mapping helps you design fast schemas.

Ranges

Every table and index is stored as a sorted sequence of key-value pairs. That keyspace is divided into contiguous chunks called ranges, each 512 MiB by default. When a range grows past its threshold, it splits; when ranges are small and adjacent, they merge.

Each range is replicated (three copies by default) and one replica holds the lease, which serves consistent reads and coordinates writes for that range.

Primary keys

The primary key determines the physical order of rows on disk and therefore how rows are distributed across ranges.

Avoid sequential primary keysMonotonically increasing keys (like SERIAL or timestamps) send every insert to the same range, creating a hotspot. Prefer UUID or a hash-sharded key.
-- Hash-sharded primary key spreads writes over 16 buckets
CREATE TABLE events (
  ts      TIMESTAMPTZ NOT NULL,
  device  UUID NOT NULL,
  payload JSONB,
  PRIMARY KEY (ts, device) USING HASH WITH (bucket_count = 16)
);

NumericINT2, INT4, INT8, FLOAT4, FLOAT8, DECIMAL

Column families

By default, all columns of a row are stored together. You can group frequently updated columns into a separate column family so updates don't rewrite large, rarely changing columns.

CREATE TABLE accounts (
  id       UUID PRIMARY KEY,
  profile  JSONB,
  balance  DECIMAL,
  FAMILY cold (id, profile),
  FAMILY hot  (balance)
);

Transactions

Basalt provides fully ACID transactions with serializable isolation, even when a transaction touches data on many nodes in many regions.

Isolation levels

LevelAnomalies preventedNotes
SERIALIZABLEAllDefault. Recommended for most workloads.
READ COMMITTEDDirty readsFewer retries under heavy contention.

Explicit transactions

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 'a1';
UPDATE accounts SET balance = balance + 100 WHERE id = 'b2';
COMMIT;

Handling retries

Under serializable isolation, conflicting transactions may be aborted with error 40001. Clients should retry these. The official drivers include a helper that does this automatically:

def transfer(tx, src, dst, amount):
    tx.execute("UPDATE accounts SET balance = balance - %s WHERE id = %s", (amount, src))
    tx.execute("UPDATE accounts SET balance = balance + %s WHERE id = %s", (amount, dst))

conn.run_transaction(lambda tx: transfer(tx, "a1", "b2", 100))
await db.runTransaction(async (tx) => {
  await tx.query("UPDATE accounts SET balance = balance - $1 WHERE id = $2", [100, "a1"]);
  await tx.query("UPDATE accounts SET balance = balance + $1 WHERE id = $2", [100, "b2"]);
});
err := basalt.RunTx(ctx, db, func(tx basalt.Tx) error {
    if _, err := tx.Exec(ctx, "UPDATE accounts SET balance = balance - $1 WHERE id = $2", 100, "a1"); err != nil {
        return err
    }
    _, err := tx.Exec(ctx, "UPDATE accounts SET balance = balance + $1 WHERE id = $2", 100, "b2")
    return err
})

Follower reads

For queries that can tolerate slightly stale data, use AS OF SYSTEM TIME to read from the nearest replica instead of the leaseholder. This can dramatically lower latency in multi-region deployments.

SELECT * FROM products AS OF SYSTEM TIME follower_read_timestamp();
TipFollower reads never block on writes and never cause transaction retries.

Indexes

Secondary indexes let Basalt find rows without scanning a whole table. Every index is itself a distributed, replicated table.

Creating indexes

CREATE INDEX products_price_idx ON products (price);

-- Covering index: avoids a lookup back to the primary table
CREATE INDEX products_tag_idx ON products (created_at DESC) STORING (name, price);

Index creation is online: reads and writes continue while the index backfills.

Index types

TypeBest forSyntax
B-treeEquality and range lookupsCREATE INDEX … (col)
InvertedJSONB, arrays, full-textCREATE INVERTED INDEX … (col)
PartialQueries on a subset of rows… WHERE condition

Inspecting query plans

EXPLAIN ANALYZE SELECT name FROM products WHERE price BETWEEN 30 AND 60;

NoteEvery index adds write amplification. Use SHOW INDEX USAGE to find and drop unused indexes.

SQL Reference

Basalt implements a large subset of PostgreSQL's SQL dialect, plus extensions for distribution and time travel.

Data definition

CREATE TABLE IF NOT EXISTS orders (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  customer_id UUID NOT NULL REFERENCES customers (id),
  total       DECIMAL(12, 2) CHECK (total >= 0),
  status      TEXT DEFAULT 'pending'
);

ALTER TABLE orders ADD COLUMN shipped_at TIMESTAMPTZ;
DROP TABLE IF EXISTS legacy_orders CASCADE;

Joins and aggregates

SELECT c.name, count(o.id) AS orders, sum(o.total) AS revenue
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'shipped'
GROUP BY c.name
HAVING sum(o.total) > 1000
ORDER BY revenue DESC
LIMIT 10;

Upserts

INSERT INTO inventory (sku, qty) VALUES ('KB-01', 5)
ON CONFLICT (sku) DO UPDATE SET qty = inventory.qty + excluded.qty;

-- Basalt shorthand
UPSERT INTO inventory (sku, qty) VALUES ('KB-01', 5);

Window functions

SELECT day, revenue,
       avg(revenue) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS rolling_7d
FROM daily_sales;

Basalt extensions

StatementPurpose
AS OF SYSTEM TIMEQuery historical data or use follower reads.
SHOW RANGES FROM TABLE tInspect how a table is split and where replicas live.
ALTER TABLE t CONFIGURE ZONESet replication factor and placement constraints.
CHANGEFEED FOR tStream row-level changes to Kafka, webhooks, or cloud storage.

Compatibility notes

The following PostgreSQL features are not currently supported: stored procedures in languages other than PL/pgSQL, LISTEN/NOTIFY (use changefeeds instead), and table inheritance.

JSON Documents

Store semi-structured data in JSONB columns and query it with full index support.

Replication & Clustering

Deploy Basalt across machines, zones, and regions for scale and resilience.

Start a three-node cluster

  1. Start each node, pointing --join at all initial members:

    basalt start --certs-dir=certs --store=/data/basalt \
  --advertise-addr=node1.internal \
  --join=node1.internal,node2.internal,node3.internal \
  --locality=region=us-east,zone=us-east-1a

  2. Initialize the cluster once, from any node:

    basalt init --certs-dir=certs --host=node1.internal

  3. Confirm all nodes are live:

    basalt node status --certs-dir=certs --host=node1.internal

Fault tolerance

A range with N replicas tolerates the loss of (N − 1) / 2 replicas.

Multi-region tables

ALTER DATABASE shop SET PRIMARY REGION 'us-east';
ALTER DATABASE shop ADD REGION 'eu-west';
ALTER DATABASE shop ADD REGION 'ap-south';

-- Rows live in the region of the user who owns them
ALTER TABLE users SET LOCALITY REGIONAL BY ROW;

-- Small, read-mostly tables: fast reads everywhere
ALTER TABLE currencies SET LOCALITY GLOBAL;
Survival goalsUse ALTER DATABASE shop SURVIVE REGION FAILURE to keep the database writable when an entire region goes offline. This requires at least three regions.

Backup & Restore

Take consistent, distributed backups without pausing writes.

Full backups

BACKUP DATABASE shop INTO 's3://my-backups/shop?AUTH=implicit'
  AS OF SYSTEM TIME '-10s';

Incremental backups

Subsequent backups to the same collection only copy data that changed since the last backup.

BACKUP DATABASE shop INTO LATEST IN 's3://my-backups/shop?AUTH=implicit';

Scheduled backups

CREATE SCHEDULE nightly
  FOR BACKUP DATABASE shop INTO 's3://my-backups/shop?AUTH=implicit'
  RECURRING '@daily'
  FULL BACKUP '@weekly'
  WITH SCHEDULE OPTIONS first_run = 'now';

Restoring

-- Restore the most recent backup
RESTORE DATABASE shop FROM LATEST IN 's3://my-backups/shop?AUTH=implicit';

-- Point-in-time restore of a single table
RESTORE TABLE shop.orders FROM LATEST IN 's3://my-backups/shop?AUTH=implicit'
  AS OF SYSTEM TIME '2026-11-10 14:00:00'
  WITH into_db = 'shop_recovery';
CautionRestoring a database requires that no database with the same name exists. Use into_db or new_db_name to restore alongside existing data.

Configuration

Basalt is configured through command-line flags, a TOML file, environment variables, and cluster settings — in that order of precedence.

Configuration file

# /etc/basalt/basalt.toml
[node]
store       = "/data/basalt"
listen-addr = "0.0.0.0:5433"
http-addr   = "0.0.0.0:8080"
locality    = "region=us-east,zone=us-east-1a"

[cache]
size = "25%"          # of system memory

[sql]
max-memory = "25%"
max-connections = 2000

[security]
certs-dir = "/etc/basalt/certs"
insecure  = false
basalt start --config=/etc/basalt/basalt.toml

Environment variables

Every flag can be set as an environment variable with the BASALT_ prefix, upper-cased, with dashes replaced by underscores. For example, --max-sql-memory becomes BASALT_MAX_SQL_MEMORY.

Cluster settings

Cluster-wide settings are stored in the database and take effect on all nodes without a restart.

Connection pooling

pool = basalt.Pool(os.environ["BASALT_URL"], min_size=4, max_size=20)
with pool.connection() as conn:
    conn.execute("SELECT 1")
const pool = new Pool({ connectionString: process.env.BASALT_URL, max: 20 });

Sizing your poolA good starting point is 4 connections per vCPU across the whole cluster, divided among your application instances.

Community drivers

Because Basalt speaks the PostgreSQL wire protocol, most Postgres drivers and ORMs work out of the box, including JDBC, psycopg, node-postgres, pgx, SQLAlchemy, Prisma, and Django. You'll need to implement retry handling for error 40001 yourself.

Error Codes

Basalt uses standard SQLSTATE codes. The most common ones, and how to handle them, are listed below.

Common errors

SQLSTATENameWhat to do
40001serialization_failureRetry the transaction. Use driver retry helpers.
40003statement_completion_unknownThe commit outcome is ambiguous. Check whether the write applied before retrying.
23505unique_violationA row with this key already exists. Consider UPSERT.
23503foreign_key_violationThe referenced row does not exist.
53200out_of_memoryIncrease --max-sql-memory or reduce query result size.
57014query_canceledStatement timeout reached or query canceled by user.
XXB01range_unavailableA range lost quorum. Check node health with basalt node status.

Retry errors in depth

Serialization failures carry a reason in the error detail that helps you diagnose contention:

ERROR: restart transaction: TransactionRetryWithProtoRefreshError: WriteTooOldError
SQLSTATE: 40001
HINT: See: https://docs.basalt.dev/transactions#handling-retries
  • WriteTooOldError — another transaction wrote the same key at a later timestamp.
  • ReadWithinUncertaintyInterval — clock skew between nodes made a value's ordering ambiguous.
  • TransactionAbortedError — a higher-priority transaction pushed this one out.
Reducing contentionKeep transactions short, avoid read-then-write patterns on hot rows, and use SELECT … FOR UPDATE to acquire locks early.
