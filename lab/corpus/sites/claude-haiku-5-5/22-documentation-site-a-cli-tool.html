Forge CLI

Forge is a command-line tool for scaffolding, building, testing, and deploying projects from a single consistent interface.

Forge reads a small configuration file at the root of your project and runs the same steps locally and in CI. It is designed to be predictable: every command prints what it is doing, returns a meaningful exit code, and can be run non-interactively.

Key features

  • One workflow for local development and continuous integration.
  • Declarative configuration in forge.yaml, versioned with your code.
  • Incremental builds that skip unchanged targets.
  • Safe deploys with dry-run previews and automatic rollback on failure.
  • Machine-readable output via --json for scripting.

Installation

Forge is distributed as a single static binary for macOS, Linux, and Windows.

Using Homebrew

bash
$ brew install forge-cli/tap/forge

Using the install script

bash
$ curl -fsSL https://example.com/forge/install.sh | sh

Verify the installation

bash
$ forge --version
# forge 3.4.1 (linux/amd64)
Requirements Forge has no runtime dependencies. Building container targets requires Docker 24 or later.

Quick start

This walkthrough creates a new project, builds it, runs the tests, and deploys to a staging environment.

1. Create a project

bash
$ forge init my-service
$ cd my-service

2. Build and test

bash
$ forge build
$ forge test

3. Deploy to staging

bash
$ forge deploy --env staging --dry-run
$ forge deploy --env staging

forge init

Creates filesSafe to re-run

Creates a new project directory with a starter forge.yaml, a sample source tree, and a .forgeignore file.

Usage

text
forge init [name] [flags]

Flags

FlagDefaultDescription
--templatebasicStarter template to use: basic, api, or worker.
--forcefalseOverwrite existing files in the target directory.
--no-gitfalseDo not initialize a Git repository.

Example

bash
$ forge init billing-api --template api

forge build

IncrementalWrites to ./dist

Compiles all targets defined in forge.yaml. Targets whose inputs have not changed since the last successful build are skipped.

Usage

text
forge build [target...] [flags]

Flags

FlagDefaultDescription
--cleanfalseRemove the dist/ directory before building.
--jobs, -jCPU countMaximum number of targets to build in parallel.
--releasefalseEnable optimizations and strip debug symbols.
--no-cachefalseIgnore the build cache and rebuild every target.

Examples

bash
# Build everything
$ forge build

# Build only the api target, optimized
$ forge build api --release

# Clean rebuild with 4 workers
$ forge build --clean -j 4

forge test

ParallelExits non-zero on failure

Runs the test suites declared under tests: in forge.yaml. Results are printed in a summary table at the end of the run.

Usage

text
forge test [suite...] [flags]

Flags

FlagDefaultDescription
--filternoneRun only tests whose names match the given pattern.
--coveragefalseCollect and report line coverage.
--fail-fastfalseStop the run after the first failing test.

Example

bash
$ forge test --filter "auth*" --coverage

forge deploy

Network accessRequires --env

Deploys the most recent build to the named environment. Forge keeps the previous release so that a failed health check triggers an automatic rollback.

Always preview first Use --dry-run to see the planned changes before applying them to production.

Usage

text
forge deploy --env <name> [flags]

Flags

FlagDefaultDescription
--envrequiredTarget environment defined in forge.yaml.
--dry-runfalsePrint the planned changes without applying them.
--no-rollbackfalseDisable automatic rollback when health checks fail.
--timeout5mMaximum time to wait for the deployment to become healthy.

Example

bash
$ forge deploy --env production --timeout 10m

forge config

Read / write

Reads and writes values in forge.yaml without opening an editor. Keys use dot notation.

Subcommands

CommandDescription
forge config get <key>Print the value of a key.
forge config set <key> <value>Set a key to a new value.
forge config listPrint the full resolved configuration.

Example

bash
$ forge config set build.jobs 8
$ forge config get build.jobs
# 8

Configuration file

Forge looks for forge.yaml in the current directory and then in each parent directory. The first file found is used.

Example

yaml
# forge.yaml
name: billing-api
version: 1.0.0

build:
  jobs: 4
  targets:
    api:
      source: ./cmd/api
      output: dist/api
    worker:
      source: ./cmd/worker
      output: dist/worker

tests:
  unit:
    command: go test ./...
  integration:
    command: go test -tags=integration ./test/...

environments:
  staging:
    url: https://staging.example.com
  production:
    url: https://api.example.com
    require_approval: true

Top-level keys

KeyTypeDescription
namestringProject name, used in output and deploy metadata.
versionstringSemantic version of the project.
buildmapBuild targets and settings.
testsmapNamed test suites and their commands.
environmentsmapDeployment environments.

Global options

These flags work with every command.

FlagDescription
-c, --config <path>Use a specific configuration file.
-v, --verbosePrint detailed logs. Repeat for more detail (-vv).
-q, --quietSuppress all output except errors.
--jsonEmit machine-readable JSON instead of formatted text.
--no-colorDisable colored output. Also respected via NO_COLOR.
-h, --helpShow help for a command.

Exit codes

Forge uses consistent exit codes so that scripts can distinguish failure types.

CodeMeaning
0Success.
1General error.
2Invalid usage or flags.
3Configuration file is missing or invalid.
4Build failed.
5Tests failed.
6Deployment failed (rollback may have run).

Environment variables

Environment variables override values in forge.yaml. Flags override both.

VariableDescription
FORGE_CONFIGPath to the configuration file.
FORGE_TOKENAPI token used for deploys. Prefer this over storing tokens in files.
FORGE_ENVDefault environment for forge deploy.
FORGE_CACHE_DIRLocation of the build cache. Defaults to ~/.cache/forge.
NO_COLORDisable colored output when set to any value.

Using Forge in CI

Forge is non-interactive when --json or --quiet is set, and it never prompts when stdin is not a terminal. A typical pipeline runs build, test, and deploy as separate steps.

Example: GitHub Actions

yaml
name: ci
on: [push]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install Forge
        run: curl -fsSL https://example.com/forge/install.sh | sh
      - run: forge build --release
      - run: forge test --coverage --json

  deploy:
    needs: build
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - uses: actions/checkout@v4
      - name: Install Forge
        run: curl -fsSL https://example.com/forge/install.sh | sh
      - run: forge deploy --env staging
        env:
          FORGE_TOKEN: ${{ secrets.FORGE_TOKEN }}

Troubleshooting

error: no forge.yaml found

Run Forge from your project directory, or pass the file explicitly with --config. Check that the file is named exactly forge.yaml, not forge.yml.

Builds are slower than expected

Run forge build -vv to see which targets are rebuilding. If the cache is being invalidated on every run, check for files that change during the build, such as generated timestamps, and add them to .forgeignore.

Deploy times out

Increase the wait with --timeout 15m. If the service never becomes healthy, check its logs; Forge will roll back automatically unless --no-rollback was set.

Authentication failed during deploy

Confirm that FORGE_TOKEN is set and has not expired. Run forge config list to verify which token source is being used.

FAQ

Does Forge send telemetry?

No. Forge does not collect usage data. Network requests are made only for deploys and for downloading optional build plugins.

Can I use Forge without Docker?

Yes. Docker is only required for targets that build container images. All other targets run natively.

How do I report a bug?

Open an issue on the project repository. Include the output of forge --version and the command you ran with -vv enabled.
